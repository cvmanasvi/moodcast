# Data provenance and licensing

This document records where MoodCast's data and models come from, under what
terms, what this project does to them, and which of them this repository
distributes. It is a provenance record, not legal advice.

## Purpose

- **Code and data are licensed separately.** The MIT License in `LICENSE`
  covers this project's source code only. It does not apply to any dataset,
  Spotify content, third-party metadata, artwork, or anything derived from
  them, including the trained models listed below.
- Each dataset keeps its own licence and its own provenance questions, which
  are evaluated per dataset in the sections below.
- Some datasets are external dependencies: they are downloaded locally, kept
  out of git, and are not part of the repository.
- **This repository distributes no third-party dataset and no model trained
  on one.** Every dataset below is provided or built locally and is
  gitignored. The only data and model files included are the
  project-generated text-mood training set and its model, and aggregate
  evaluation reports.

## 278k Moodify dataset

| | |
|---|---|
| Name | 278k Emotion Labeled Spotify Songs |
| Author | Abdullah Orzan |
| Source | Kaggle, https://www.kaggle.com/datasets/abdullahorzan/moodify-dataset (Moodify project, https://github.com/orzanai/Moodify) |
| Licence | Creative Commons Attribution 4.0 International (CC BY 4.0), https://creativecommons.org/licenses/by/4.0/ |
| Version | Kaggle version 2, 2023-05-31 |
| Local path | `data/music_dataset2/278k_labelled_uri.csv` (gitignored; not in this repository) |
| SHA-256 of the copy this project used | `0b7c864e7de8d16eaf2c284af5ba7c3bce77a0e6f72a275b774e361bc40e1b02` (not re-verified against a fresh Kaggle download) |
| Rows | 277,938 |

**What this project uses from it**

- **Track IDs**: the `uri` column (`spotify:track:<id>`), which becomes the
  canonical `track_id`.
- **Audio features**: `duration (ms)`, `danceability`, `energy`, `loudness`,
  `speechiness`, `acousticness`, `instrumentalness`, `liveness`, `valence`,
  `tempo`. The Moodify project describes its songs as obtained through the
  Spotify API, so these are Spotify-derived audio features.
- **Labels**: `labels`, 0 = sad, 1 = happy, 2 = energetic, 3 = calm. The
  dataset's Kaggle description attributes the emotion labels to a model
  (LightGBM) built by the Moodify project, so they should be read as
  model-generated labels rather than per-track human annotations. Accuracy
  figures reported by this project measure agreement with those labels.

`278k_song_labelled.csv` holds the same rows and columns without `uri`. Since
Phase 2H.4 no code reads it, so you don't need it.

**How this project transforms it**: see
[Derived 278k catalog](#derived-278k-catalog). The source files themselves are
never modified (the pipeline checks the source's SHA-256 before and after each
run).

**CC BY 4.0 requirements.** Sharing or adapting this dataset requires:

- **Attribution**: credit the creator and the source (see [Attribution](#attribution)).
- **Licence link**: provide a link to the CC BY 4.0 licence.
- **Indication of changes**: say whether and how the material was modified.
- **No additional restrictions**: no legal terms or technological measures
  that restrict others from doing what the licence permits.

**Provenance caveat.** Although the upstream dataset is identified as CC BY
4.0, this project does not make an independent legal determination that all
underlying Spotify-derived rights are cleared for redistribution. A CC licence
covers only the rights its licensor holds, and the track IDs and audio
features originate from Spotify, whose platform terms are separate (see
[Spotify policy caveat](#spotify-policy-caveat)).

## Derived 278k catalog

`data/music_catalog_278k.csv` (277,938 rows) is generated from
`data/music_dataset2/278k_labelled_uri.csv` by `train_music_278k.py` using
`src/music_pipeline.py`. It is a derived (adapted) artifact and inherits the
upstream provenance considerations above, so it is built locally rather than
distributed. From the source file recorded above, the build is deterministic
and reproduces the catalog SHA-256 recorded in `models/*.json`
(`a261afeea3b11859cd5a8cdb65fc12402a08b8dc4e684b670c791c0dd2af9a6a`; the
catalog is written with LF line endings on every platform).

Changes from the source:

- Spotify URI → `track_id` (the `spotify:track:` prefix is removed; row order
  and labels are unchanged).
- `labels` kept as `label`; added `mood` (the label's name).
- Added classifier probabilities `proba_sad`, `proba_happy`,
  `proba_energetic`, `proba_calm`, from this project's
  `models/music_mood_classifier_278k.pkl`.
- Added `predicted_mood` and `mood_confidence` from the same classifier.
- Added `derived_angry` and `derived_angry_score` (a feature-percentile rule;
  the source has no angry label).
- Added `derived_stressed` and `derived_stressed_score` (an experimental
  feature rule; the source has no stressed label).
- Removed `spec_rate` and the index columns; `duration (ms)` is renamed
  `duration_ms`.

The catalog contains no titles, artists, albums, artwork or popularity.

## Local metadata

`data/metadata/` (`music_metadata.csv` and the provenance manifest
`metadata_sources.json`) is gitignored, local-only and should not be treated
as a public dataset. It is built by `build_music_metadata.py` from **Spotify
Dataset 1921-2020, 600k+ Tracks** by Yamac Eren Ay
(https://www.kaggle.com/datasets/yamaerenay/spotify-dataset-19212020-600k-tracks),
licensed **CDLA-Sharing-1.0**. Only track title, artists and release year are
extracted, for exact `track_id` matches.

That creator describes the data as collected from the Spotify Web API; the
licence covers the creator's dataset and does not by itself establish rights
in the underlying Spotify data. See `METADATA.md` for the build, matching
rules and columns.

## External datasets

`data/external/` holds downloaded third-party datasets used by offline build
and analysis scripts. It is intentionally gitignored and is not part of the
repository. Only datasets documented in this file or `METADATA.md` are used
by the project's pipelines; anything else there was evaluated and not
adopted.

## Legacy Spotify API data (retired)

`data/music_final.csv` and `data/music_final_rulebased_backup.csv` (1,023
tracks each) were legacy artifacts from the project's original pipeline
(`build_simple_spotify.py`), which collected tracks from the Spotify Web API
search endpoint. They contained Spotify API-derived track titles, artist
names, album names, popularity, durations and album-artwork URLs hosted on
Spotify's image CDN (`i.scdn.co`).

Phase 2H.4 removed both files, the model fitted on them
(`models/music_local_kmeans.pkl`), the Streamlit app and the rollback switch
that used them, all Spotify collector code (`build_simple_spotify.py`,
`build_spotify_dataset.py`, `update_music.py`, `test_spotify.py`,
`src/spotify_client.py`, and the music builder in `src/build_datasets.py`,
which now builds movies only) and the Spotify API configuration. None of them
is part of this repository (see
[Public repository cleanup](#public-repository-cleanup)).

### Synthetic features

The audio-feature columns in the legacy files (`valence`, `energy`,
`danceability`, `tempo`, `acousticness`, `instrumentalness`, `liveness`,
`speechiness`, `loudness`) were **synthetic**. The old pipeline generated them
with random values inside fixed per-mood ranges
(`_generate_synthetic_features` in `build_simple_spotify.py`); they were not
Spotify audio features and did not describe the actual recordings.

## Movie data

`data/movie_dataset2/Movies (1970-2023).csv` (21,895 rows) holds titles, IMDb
IDs, cast, plot text, ratings, votes and poster URLs on `m.media-amazon.com`.
`data/movies_final.csv` and `data/movies_final_rulebased_backup.csv`
(12,586 rows each) are derived from it by `src/build_datasets.py` and
`train_all_models.py`. **Where the raw file came from and under what licence
are not recorded anywhere in this project.** Its content (IMDb identifiers,
plot summaries, Amazon-hosted poster images) may be subject to third-party
rights. So none of these files, nor `models/movie_mood_classifier.pkl`
trained on them, is distributed, and no licence is claimed for them.

Without `data/movies_final.csv`, movie recommendations answer with an
explanation (HTTP 503) and search returns no movies. `build_tmdb_dataset.py`
(TMDB API, your own key, under TMDB's terms) writes a different schema and
is not a verified replacement.

## Popular Artists dataset

The Music page's **Popular Artists** mode uses its own dataset, separate from
the 278k catalog and the local metadata.

| | |
|---|---|
| Dataset | Spotify Tracks Dataset (Updated every week) |
| Creator | Gautham Vijayaraj |
| URL | https://www.kaggle.com/datasets/gauthamvijayaraj/spotify-tracks-dataset-updated-every-week |
| Version | Kaggle version 2, 2024-12-09 (the title says "updated every week", but it has not changed since) |
| File | `spotify_tracks.csv`, SHA-256 `2bdeea651ed626f89c034a1bb0c343ad47350ad852950c575f941f38da8d5f9d` |
| Licence | Apache 2.0, as stated by the author on Kaggle |
| Collection method | Not documented by the author |
| Local files | `data/external/popular_artists_2024/` (raw `spotify_tracks.csv`, prepared `popular_tracks.csv`, `manifest.json`) |

**Rights.** The Apache 2.0 licence is the dataset author's licence and covers
only what the author can license. The author does not say how the data was
collected; its fields (Spotify track IDs, audio features, popularity, Spotify
artwork links) are Spotify track data, which may be governed by Spotify's
terms separately from that licence (see the caveat below). The licence does
not resolve that question and this project does not claim it does. So:

- The raw and prepared files are local-only (`data/external/` is gitignored)
  and are never committed or redistributed. The repository holds only the
  preparation script, the curated artist names (`config/popular_artists.json`)
  and this documentation.
- The dataset's `artwork_url` column is not used. Covers are shown only via
  the app's existing on-demand oEmbed lookup for tracks on screen, never
  stored; otherwise the card shows its placeholder.
- If the data were ever redistributed, Apache 2.0 would require including the
  licence and attributing the author, and the Spotify question would have to
  be resolved first.

**Preparing it.** From the project root, with one of:

    python prepare_popular_artists.py --source path/to/spotify_tracks.csv   # or the Kaggle .zip
    python prepare_popular_artists.py --download                            # opt-in; fetches version 2 from Kaggle
    python prepare_popular_artists.py                                       # raw file already in place

Every input must match the SHA-256 above or preparation stops and writes
nothing. The script checks the exact schema (22 columns, numeric fields) and
drops rows with malformed track IDs, a `track_url` that is not exactly
`https://open.spotify.com/track/<track_id>`, placeholder or out-of-range
values (the source marks missing values `-1`; `-100000` also occurs), tracks
under a minute, spoken word (speechiness > 0.66) or failed audio analysis.
Duplicate IDs are kept once when identical and dropped when they disagree.
Only tracks whose artist string contains a curated name as a whole
comma-separated entry are kept: names are never split on commas
("Tyler, The Creator" stays one name) and never matched partially ("Pritam"
does not match "Pritam Chakraborty"). The artist string is displayed exactly
as the source has it. Versions of one recording (same artist string, title
and duration to the second, typically the same song on many compilation
albums) collapse to the most popular. The 2026-10-10 build kept 12,518 of
62,317 rows; `manifest.json` records every count and contains no track IDs.

**Moods are model-derived, not human-validated.** Happy, sad, energetic and
calm (chill) come from MoodCast's existing 278k classifier
(`models/music_mood_classifier_278k.pkl`, 83.5% agreement with its training
labels): a track qualifies with probability >= 0.6 (calm also excludes
speech-like tracks). Angry and stressed use the existing derived-mood rules
with the cutoffs recorded for the 278k catalog in
`models/music_mood_classifier_278k_eval.json`, never recomputed on this data;
preparation stops if those records no longer match the catalog. Coverage for
"Match my mood" in the 2026-10-10 build (tracks; international / K-pop /
Indian): happy 6,318 (898 / 1,947 / 3,473), sad 3,139 (491 / 260 / 2,388),
energetic 996 (200 / 585 / 211), chill 296 (23 / 13 / 260), angry 108
(34 / 51 / 23), stressed 493 (151 / 103 / 239). Chill is mostly Indian and
angry is small; lists say so when they run short rather than adding tracks
that don't fit.

## Spotify policy caveat

- Content obtained from Spotify is governed by Spotify's own platform terms
  and developer policy, separately from any dataset licence:
  https://developer.spotify.com/terms and
  https://developer.spotify.com/policy.
- MoodCast does not call the Spotify Web API. Recommendation, mood
  classification and ranking run entirely on local files, and Spotify links
  are built from `track_id` alone. The one runtime call to Spotify is the
  public oEmbed endpoint (no login, token or Premium), used only to show the
  real title and cover of tracks on screen, cached in memory and never
  stored (approved 2026-10-09; see `METADATA.md`, disable with
  `MOODCAST_SPOTIFY_OEMBED=0`).
- The current architecture deliberately avoids fetching Spotify API content
  for training or at runtime.
- How Spotify's terms apply to third-party datasets that were originally
  collected from Spotify (such as the 278k and 600k datasets, and the
  Popular Artists dataset) is a separate, unresolved question that this
  project does not answer.
